## オーディオ: `WAVEFORM_BUFFER`への波形書き込み

**状態:** 実装済み(`waveform.rs`/`music.rs`。未決定事項のパラメータ調整とメロディ作成は実機での確認待ち)

**仕様:**

- 波形出力モジュールとして、波形出力用の slot を２個作成する
    - slot は、波形データの先頭から、位相情報に合わせてデータを読み込む
    - slot は、note on message を受信し、これをトリガにして波形を出力する
    - note on message には、pitch, volume, duration の３つのデータがある
        - pitch は、波形を読み込むための1サンプルあたりの位相情報を変更する(69で波形データを一つずつ読む位相となる)。MIDI Note Number 69(=A4=440Hz)を基準に、位相増分 = 2^((pitch - 69) / 12) として計算する
        - volume は、音量で 1-127 の範囲、振幅は (volume/127)^2 とする
        - duration は、音を消し始めるタイミングを制御する
    - slot に note on message が来たら、振幅ゼロから attack rate に従って、少しずつ振幅を上げていく
    - slot が鳴り始めて duration だけ経過したら最大振幅から release rate に従って、少しずつ振幅を下げていく
    - 振幅がある一定値以下(minimum level)になったら、振幅はゼロにする
    - 一つの slot が発音中に新しい note on message が来た時、現在の音を damp rate で急速に消音し、振幅が minimum level 以下になったら、attack rate に従って note on message を開始する
        - damp 中は前の音の pitch で、attack が始まったら新しい pitch で発音する
        - damp rate 中にさらに新しい note on message が来たら、次になる音を新しい note on message に差し替える
    - WAVEFORM_BUFFER のDMA転送が終わったことを確認できたら、AUDIO_BUFFER_SAMPLES 分の二つの slot のバッファの値を足して、その値を WAVEFORM_BUFFER に書き込む
        - 「DMA転送が終わったこと」の確認には Signal を使う。既存の DMA 転送ループ(`i2s.write().await` が返った直後)が Signal を発行し、波形出力モジュールはこれを待ってから次のチャンクを合成・書き込みする。Signal は最新の1回分の通知のみを保持するため、波形出力モジュールが多少速くても遅くても、実際の再生ペースと1:1でずれずに同期できる
    - バッファの値を足した結果がオーバーフローした場合、最大値に張り付く
- 音楽データ再生モジュールを作成する
    - 音楽データは、note on message の集まりであり、time, pitch, volume, duration の４つのデータを複数個持ったものである
        - time: 0 から始まり、再生開始からの時間を表す(1=10msec)
        - pitch: 0-127 の MIDI の Note Number
        - volume: 1-127
        - duration: この note on message が開始してから消音するまでの時間を、time と同じ単位で記述する
    - 読み出したデータは、note on message として二つの slot に交互に送られる
    - 音楽データは全部で５つある
    - このモジュールは、event によって再生開始し、event は 0-4 の値を持っており、その値で音楽データを指定する
    - ボタンを押すと、押したボタン(person_idx、0-4)に対応する音楽データが発音する。つまりボタンごとに別々のメロディが鳴る
    - モジュールが再生中に新しい event が来たら、引数に合った新しい音楽データを再生開始する
        - slot に対して消音するなど、特別な処理は特に行わない
- 波形出力モジュールと音楽データ再生モジュールは、同じ core 内で、別タスクとして実装する
- core0 から core1 に、音楽データ再生モジュールを駆動する event を送る仕組みを作成する(Channelを使用)
    - 実装済み: `events.rs::MELODY_CHANNEL`(`Channel<CriticalSectionRawMutex, usize, 8>`)を新設し、`buttons.rs`のボタン押下処理から person_idx を送信する。CORE1側では音楽データ再生モジュール(`music.rs`の`music_task`)がこのチャネルを受信して再生を開始する
- 用意するデータ
    - slot 用の波形データ(一波分、サイン波、100サンプル) — 実装済み(`waveform.rs`の`WAVETABLE`)
    - 5つの音楽データ — 実装済み(`music.rs`の`MELODY_0`〜`MELODY_4`)。ただし現状はプレースホルダの短い旋律で、実際の曲ではない
- サンプリング周波数(`AUDIO_SAMPLE_RATE_HZ`)は 44,000Hz とする(一般的なオーディオ規格に合わせる必要がないため、440Hz(MIDI Note 69 = A4)の整数倍を採用)。これにより pitch=69 の波形テーブルがピッチ誤差ゼロで100サンプルぴったりになり、波形データの作成や、将来別の楽器/音色への転用がしやすくなる
- attack/release/damp の動作は、時間に対して一定割合で目標に近づく漸近的カーブとする
    - この「一定割合」は1サンプルごとに適用する(チャンク単位ではない)。RP2350のCPU性能に対して1サンプルごとの演算負荷は十分小さく(1サンプルあたり数千サイクルの余裕がある)、チャンク単位更新による振幅の階段状変化(zipper noise)を避けられるため


**未決定事項:**
- attack rate(現状は`config.rs`の`AUDIO_ATTACK_RATE`=0.01、実機で聴いて調整するまでの仮値)
- release rate(同`AUDIO_RELEASE_RATE`=0.002、仮値)
- damp rate(同`AUDIO_DAMP_RATE`=0.05、仮値)
- minimum level(同`AUDIO_MINIMUM_LEVEL`=0.001、仮値)
- 5つの音楽データの実際の旋律(現状はプレースホルダ)

## オンボードLEDのハートビート点滅

**状態:** 実装済み(`wifi.rs`。1Hzの点滅は実機で確認済み。接続試行中の点灯と失敗時の「ピピ」の見え方は未確認)

**仕様:**

- Raspberry Pi Pico 2 W基板上のオンボードLEDで、ファームウェアが動作していることと、Wi-Fi接続の成否を、基板を見るだけで確認できるようにする
- LEDの状態は次のとおりとする

| 状況 | オンボードLED |
|---|---|
| Wi-Fi接続試行(`join`)の実行中 | 点灯したまま |
| 接続試行に成功したあと(接続の監視中) | 1Hz(500ms点灯 / 500ms消灯)の点滅を続ける |
| 接続試行に失敗したあと(次の試行までの待機中) | 「ピピ」(短い点滅2回のあと、しばらく消灯)を繰り返す |

- 失敗の「ピピ」は、接続試行が失敗した直後から始め、次の接続試行が始まる(LEDが点灯に変わる)まで繰り返す。接続に失敗し続けている間は、「点灯 → ピピ、ピピ、…(次の試行まで) → 点灯 → …」の繰り返しになり、成功後の1Hzの点滅とは見分けがつく
- 1Hzの点滅は、接続試行に成功していれば続ける。サーバーとの通信の成否とは無関係で、サーバーが停止していても点滅する
- オンボードLEDはRP2350のGPIOではなくWi-FiチップCYW43439のGPIO0(`WL_GPIO0`)に接続されているため、cyw43の`Control`経由で制御する。外部配線は不要で、`docs/wiring.md`のGPIO割り当てとも競合しない
- 接続試行の実行中に点灯したままにするのは、`join`が`Control`を占有し、完了まで戻らないため。cyw43の`join`自体にはタイムアウトがなく、チップが結果を返さないと永久に戻らないため、ファームウェア側で一定時間(`WIFI_JOIN_TIMEOUT_SECS`)を超えた接続試行を打ち切り、失敗として扱う(この場合の「ピピ」も同じ)。実機で、`join`が戻らずLEDが点灯したままになる現象を確認したための対応
- LEDの制御はCORE0のエグゼキュータ上で、`Control`を所有するタスクが行う。`Control`は`&mut`でしか使えず、Wi-Fiの接続/再接続処理も同じ`Control`を使うため、LED専用タスクは持たず、Wi-Fi管理タスク(下記)が兼ねる。CORE0のエグゼキュータが動かなくなった場合(`panic-halt`によるパニック停止を含む)は、LEDの動きが止まる(点灯か消灯のまま固まる)ため、異常の検知にも使える。CORE1(オーディオ)が動いているかどうかは反映しない

**未決定事項:**
- 接続試行のタイムアウト(`WIFI_JOIN_TIMEOUT_SECS`=20秒)は仮の値。なお、実機で、起動直後の最初の`join`が戻らず、タイムアウト後の2回目で接続できることを確認した(2026-09-19)。戻らない原因(ルーターの認証方式(WPA2/WPA3)や設定との相性、チップの初期化直後の状態など)は未特定で、タイムアウトは症状への対処であり、原因の解消ではない。起動のたびに起きるなら、接続まで約20秒余分にかかる
- 各パターンの時間は仮の値で、実機で見て変更してよい(`config.rs`)。1Hzの点滅(`ONBOARD_LED_BLINK_HALF_PERIOD_MS`=500)、「ピピ」の1回分の点灯/消灯(`ONBOARD_LED_FAIL_FLASH_MS`=100)、「ピピ」の繰り返しの間隔(`ONBOARD_LED_FAIL_PATTERN_GAP_MS`=1600)
- 接続試行に成功したが、まだDHCPが完了していない間(`wifi::is_connected()`はまだ`false`)も、成功として1Hzで点滅する

## Wi-Fi接続状態に依存しない動作

**状態:** 実装済み(`wifi.rs`/`outbox.rs`/`http_client.rs`/`status_poll.rs`ほか。実機で確認済み: 接続後のボタン押下がサーバーに届くこと、接続が完了する前の押下が接続後に届くこと。未確認: 切断後の再接続、オフライン中・サーバー停止中の押下の再送、在室の送信、NeoPixelの同期)

**仕様:**

- 基本方針: すべてのハードウェア(ボタン、NeoPixel、オーディオ、照度センサー、オンボードLED)は、Wi-Fiが接続されているか否かに関わらず、起動直後から動作する。Wi-Fi接続の完了を待って他のタスクの起動を遅らせることはしない(現状は`net::init`が接続完了まで戻らず、その間ボタン等が一切動かないため、これを改める)
- Wi-Fiの接続状態を表すグローバル変数を設ける
    - 「接続済み」は、リンクが上がっており、かつDHCPによるIPアドレス取得が完了した状態とする(`join`に成功しただけでは接続済みとしない)
    - 切断を検知したら「未接続」に戻す
    - 更新するのはWi-Fi管理タスクだけとし、ほかのタスクは読み取るだけにする。送信を行うタスクが、接続済みになるのを待てる形にする
- 未接続の間は、サーバーへのメッセージ(`POST /api/press`、`POST /api/occupancy`、`GET /api/led-state`)を送らない
- Wi-Fi管理タスクを設け、`cyw43::Control`を所有させる
    - 起動時にWi-Fiへ接続する。失敗時は指数バックオフでリトライする(現状の`net.rs`と同じ)
    - 接続後に切断を検知したら再接続する(現状は起動時に1回`join`するだけで、切断後は誰も再接続しないため、ルーターの再起動などで一度切れると電源を入れ直すまで送信できない)
    - オンボードLEDの点滅(前項「オンボードLEDのハートビート点滅」)も兼ねる
- ローカルの動作(NeoPixelの点灯、メロディの再生)は、ネットワークの状態、送信の成否、送信待ちの状態のいずれにも依存しない。ボタン押下の処理はローカルの反応を先に行い、ネットワーク側の処理で待たされないようにする(現状は、送信待ちのチャンネルが満杯になるとボタンタスクが止まり、LEDもメロディも出なくなる)
- ボタン押下の扱い
    - 人ごとの「未送信」の状態(5人分)として保持する。キューではないので溢れず、同じ人の複数回の押下は1つにまとまる(サーバー側も同日中の再押下は冪等)
    - 接続済みの間、送信タスクは未送信の人を順に`POST /api/press`し、2xxが返ったら未送信を下ろす。失敗(接続失敗、タイムアウト、5xxなど)したら未送信のまま残し、一定間隔で再試行する。Wi-Fiは接続済みでサーバーだけが停止している場合も同様に再送する(従来は失敗しても捨てていたため、Wi-Fiが生きていても押下が失われた)
    - 4xxが返った場合(人物IDの不一致など)は、再送しても成功しないため、ログに残して破棄する
    - 押した直後のNeoPixel点灯は、Wi-Fiの状態に関わらず行う
    - `/api/led-state`による同期(Sync)は、未送信の人のLEDを消さない(サーバー状態と未送信の押下のORを表示する)。これがないと、オフライン中に押した人のLEDが再接続後の同期で消えてしまう
- 在室(照度センサー)の扱い
    - 最後にサーバーへ送信成功した在室状態を保持する。現在値がそれと異なる場合に限り、接続済みの間に現在値を送る
    - オフライン中の途中の変化(例: 入室→退室)は失われる
    - 起動直後は最後に送信した値が不明なため、従来どおり、最初の変化があるまで送らない
    - 4xxが返った場合は、押下と同様にログに残して破棄する
- サーバーへの送信は、必ずタイムアウトして戻ること(相手に届かない場合に、送信タスクが長時間止まらないようにする)
- 許容する制限
    - サーバーが受理したのに応答がタイムアウトした場合、同じ内容を再送する。押下は冪等なので影響はないが、在室は同じ状態が2回記録されうる(サーバーが重複排除をしないため)
    - サーバーは受信した時刻を記録し、基板には時計がないため、オフライン中の押下や在室変化の記録時刻は、送信に成功した時刻になる。深夜0時をまたいで送信された押下は、翌日の記録になる
    - オフラインで起動した場合、既に押した人のNeoPixelも、最初の同期に成功するまでは消灯のままになる(基板に永続ストレージがないため)。その間に再度押しても、同日中の押下は冪等で害はない
    - 送信に必要な`embassy_net::Stack`はWi-Fi接続前に作成できるため、送信/同期タスクは起動時に生成し、接続済みになるまで待機させる

**未決定事項:**(現状の実装での扱いを併記)
- 未送信の押下を保持し続ける期限 — 現状は無期限。長時間オフラインだった後の送信は、実際の押下とは別の日の記録になりうる
- 起動直後の在室状態を、最初の接続時に一度サーバーへ送るかどうか — 現状は送らない。サーバーは重複排除をしないため、送ると再起動のたびに在室ログが1行増える一方、送らないと再起動後に最初の変化があるまでサーバー側の在室状態が実際とずれる可能性がある
- 送信のタイムアウト値、再試行間隔、再接続後のリンク待ち猶予 — 現状は`config.rs`の`SERVER_REQUEST_TIMEOUT_SECS`=10、`SEND_RETRY_INTERVAL_SECS`=5、`WIFI_LINK_UP_GRACE_SECS`=10。いずれも仮の値で、実機で確認して調整する
- 切断後の再接続は、`leave`を挟まずに`join`を呼び直している(実機では未確認。接続試行がタイムアウトした後は`leave`を挟んで再試行し、その2回目で接続できることを実機で確認した)
